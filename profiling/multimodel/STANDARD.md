# 多模型、多设备验证的验收标准

这份文件在**测量之前**写定，测完不改。任何一条不满足，就在结果里写"不满足"，
不改判据、不改口径。

判据的阈值全部来自仓库里已有的合同，不是这次新定的：

| 来源 | 常量 |
|---|---|
| `profiling/dac_validation/e2a.py` | `QUALITY`：过程均值 APE ≤ 10%、试次均值 P90 APE ≤ 20%、过程内试次 CV ≤ 10%、观测器相对均值差 ≤ 5% |
| `profiling/model_swap/README.md` §4 | 成本表无 `null`、未知 workspace 不得当 0、不得跨形状复用价格 |
| `profiling/decision_margin/README.md` | 预测值必须能由坐标键逐位复算 |

## 1. 每个模型能支撑到哪一步

这决定了结果怎么写，不能混。发布表就是六个模型：三个 dense、三个 MoE
（`models.json`，由 `test_the_set_is_three_dense_and_three_sparse` 钉住）。它们的结论强度**不一样**：

| 类别 | 模型 | 走哪条链路 | 能说的话 |
|---|---|---|---|
| Dense 全层 `full_causal` | Qwen3-0.6B / 1.7B / 4B | M2 的 `projection → attention → dense_ffn` 切片，逐形状实测成本 | 整模型在已实现切片上的预测误差 |
| MoE | granite-3.0-3b-a800m / Qwen1.5-MoE-A2.7B / OLMoE-1B-7B-0924 | 独立测量子图（`profiling/MOE_MEASUREMENT.md`）；块契约 `ggml_cpu_moe_decoder_block_v1` | **只能**说测量块抽象对 MoE FFN 的误差 |

**MoE 不能填 `.6` 整层成本表。** `m2-layer-0.6` 的 `costs.py` 只接受
`provenance="synthetic_layer"`，实测 MoE 成本没有可装载的边界。谁把 MoE 的实测
数字写进 `.6` 表，谁的"整层预测"就是假的。

**不能声称整模型级结论的**：任何含 `recurrent_linear` 或 `sliding_window` 层的
模型。Qwen3.5 系列（本地五个文件全是 `full_attention_interval=4` 的 hybrid）、
Granite-4.0-H-Tiny（40 层里 36 层 Mamba-2）、Trinity-Nano-Preview（2048 滑窗）
因此都不在这套验证里。理由不是"跑不动"，是**成本表没有那一项**。

## 2. 判据

### R1 字节身份

测量前 `fetch_models.py --check` 必须对每个模型报 `ok`。SHA-256 与大小都要对上
`models.json`。任何一条不符，该模型的结果作废，不是"近似可用"。

> 为什么：Q4_K_M 是同一名字下最容易被换掉的量。换过权重的模型几何相同、误差不同。

### R2 结构身份

`build_model.py --gguf` 从**本机这份文件**读出的 geometry 必须与 `models.json`
的 `geometry` 逐字段相等：`block_count`、`hidden_size`、`intermediate_size`、
`heads`、`kv_heads`、`head_dim`、`experts`、`top_k`。不等就停下，不要继续测。

### R3 价格属于设备

每个价格条目都带 `device` 字段（设备 id）。不同设备的条目**不许合并统计**，
也不许把一台机器的价格搬到另一台的报告里。`devices/<id>.json` 是唯一允许
跨设备比较的对象，它只有结构性事实（核数、内存、互联），没有价格。

**一张表什么时候要重测。** 价格是 `(设备, 线程数, 实现路径, KV dtype, 模型)` 的实测边际
成本：同几何的 0.6b/1.7b 在 4 线程下差 1.01× 而在 2 线程下差 1.28×；`-fa 0` 与 `-fa 1`
把 decode 斜率从 20.52 推到 36.09 µs/token。**这五项不变，表就不重测**——一次准确度迭代
动的是组装层或墙钟，不是表。任一项变了（换机器、改 `-t`、开关 flash attention、换 KV
元素类型、换模型），要在那台机器、那套配置下重新测，不能沿用旧表。组织上：表是一台设备
的固定资产，**一台设备测一次、多次用**；每个声明项的取值同理（探针或扫参跑一次，写进
`composition_terms`）。

### R4 不跨形状插值

成本表的键是 `(kind, device, phase, batch, tokens, visible_history)`。新形状
重新测，不许按线性或按比例从邻近形状推。缺条目就是 `null`（执行时会被拒），
不是 0。

### R5 稳定性闸门

每个键至少 20 个试次；过程内 CV > 10% 的条目自动降级为 `validation_only`，
不进主结果。降级条目要在报告里单独列出数量，不能只说"平均值"。

### R6 过程均值 APE ≤ 10%

按**每次重复各自打分**再平均，不是先平均再打分。两者在方差大时会给出不同
结论，口径固定为前者。

### R7 试次均值 P90 APE ≤ 20%

单次调用的分布尾部也要在界内。只报均值会藏掉长尾。

### R8 观测器相对均值差 ≤ 5%

外部观测（wall clock）与内部计时（CUDA event / `QueryThreadCycleTime`）之差。
超过 5% 时先说清是哪一个口径在报数，不要混用两种仪器的数字做分解。

### R9 MoE 边界

MoE 结果只能以"测量块 FFN 子图"的形式报告。路由轨迹必须来自**同一次**
被计时的那次调用（`ffn_moe_topk` 是跨步 VIEW，线性读会得到假的均匀路由）。
`moe_measured.py` 是现有唯一合法的封装。

### R10 预测可复算

`predictions.json` 里每条动作的坐标键按成本表求和，必须**逐位等于**存储的
`duration_ns`。残差不为 0 说明缓存或路径出了错，先修再报。

### R11 预注册

每个（模型，工作负载）的预测值在测量目标时延**之前**写入
`results/<campaign>/predicted.json`，带文件时间戳与设备 id。事后改预测等于
没预测。

### R12 失败保留在分母里

跑崩的进程、超时的试次都要留在记录里。`e2a.py` 的 `SEQUENCES` 与"每个失败
进程都保留"是既有做法，新战役沿用。

### R13 线程放置必须受控并记录（2026-11-03 追加）

这是**协议**的追加，不是判据的放宽：R1–R12 一个字没改。

原因：本机第一次全套测量里，`projection` 与 `dense_ffn` 的 decode 形状不读 KV，
改 `visible_history` 计算量完全不变，但同一次运行内中位耗时相差 **2.05 倍**
（4b projection h512 = 487.9 µs，h128 = 1001.7 µs），而每个 case 内 20 个样本的
CV 只有 0.008–0.030。慢档在两次重跑之间**换 case**（run1 的 h128 慢，run2 变成
h1024 慢），说明它属于进程，不属于形状。

A/B（4 个同工作量形状 ×3 次重复）给出机制：

| 配置 | 离散度 | 中位 |
|---|---|---|
| 不指定掩码 | 1.13–1.76× | 双峰，随机抽 |
| `2,4` 两个物理核 | 1.01–1.02× | ~570 µs |
| `2,3` 同一核的两个 SMT 兄弟 | 1.02–1.17× | ~1005 µs |

两个档的比值 1.76× = 两个物理核 vs 一个核的两个超线程。

所以：

- 每次测量必须显式给 `--cpu-mask`，且 `mask` 的长度等于 threads；不给掩码的
  结果是**未受控放置**，只能进对照，不能进主结果。
- 探针必须回读校验：每个进程线程的掩码都在请求集合内，且每个请求的 CPU 都被
  单 CPU 线程覆盖。只在计时之前校验一次。
- 设备分支的 `devices/<id>.json` 之外，campaign 的 manifest 必须记录
  `protocol.cpu_mask` 与 `protocol.thread_placement`；跨设备比较的是"两个物理核"，
  不是某两个具体编号。
- 换设备时要先查拓扑（`ggml-dense-layer-probe --cpu-topology`）：SMT 兄弟的编号
  不一定相邻，掩码必须落在不同的 `core_index` 上。

**没做、也不许声称的**：这次没有重编 GGML（本机是 `GGML_OPENMP=ON`，探针记录的
`thread_management` 标签对 OpenMP 构建不准确）。计时口径不受影响，标签问题如实
记在战役报告里。

### R13 同一条纪律适用于墙钟（2026-11-05 追加）

探针侧钉住了线程放置，墙钟侧也必须钉住"跑的是哪个实现"。`llama-bench` 的 JSON
行能回显的东西一律**断言**，不能回显的东西一律**显式传并记进 `measured.json`**：

| 参数 | 值 | 怎么处理 | 不钉住的后果 |
|---|---|---|---|
| `-fa` | `0` | 回显 `flash_attn`，断言 | 本机实测：换成 `-fa 1` 把 decode 斜率从 20.52 推到 36.09 µs/KV token（**1.76×**），而协议名一个字节都不变 |
| `-ctk` / `-ctv` | `f16` | 回显 `type_k`/`type_v`，断言 | 成本表声明的是 f16 缓存（`dense_contract.KV_DTYPE`）；换成 q8_0 就是另一个字节数、另一个问题 |
| `-mmp` / `-b` / `-ub` / `--poll` | `1` / `2048` / `512` / `50` | 显式传 + 写进 `bench_protocol.pinned_not_echoed` | llama-bench **完全不回显**这几项，只能声明，不能证明 |

`predict` 会把成本表声明的 `kv_dtype` 带进 `predicted.json`，`compare` 拿它与
墙钟行的 `type_k` 对照，不一致就拒绝比较——两个不同字节数的结果不能相减。

**已有的战役数字不受影响**：以上取值全部等于该构建的文档默认值，加的是"说清楚"
和"下次变了会报错"，不是改数。

**decode 的斜率要么同进程，要么写清是四个进程拼的。**`-d` 支持逗号列表，所以
`measure --group-decode` 会把一个模型的全部 decode 深度放进**一次** llama-bench
调用：四个点共享同一个机器状态，截距与斜率不再跨进程拟合。这一条不改变任何价格，
只改变"斜率这个数是从几个状态里算出来的"，所以：

- 默认仍是逐形状一个进程（历史口径），`measured.json` 的 `decode_grouping` 必须
  写明是哪一种；
- 两种分组**不能**写进同一个 `measured.json`（与线程/掩码/`bench_protocol` 同等对待）；
- 同一组里的形状必须共用 `-r`，否则拒绝——`-r` 是每次调用的参数，不是每行的。

**分组模式丢掉第一个形状的首样本（2026-11-05 实测）。** 一个 llama-bench 进程里
最先被计时的那个形状，第一个 decode 要走进程的首次解码路径，比它自己后面的样本
贵得多。OLMoE、`-t 2`、`-C 0x14`、三次独立运行：

| 位置 | 首样本 − 其余样本均值 |
|---|---|
| 一次进程里的**第一个**形状 | +13.2 ms（r5）、+10.8 ms（r8）、+4.4 ms（反序，1024 在前） |
| 同一进程里**后面**的形状 | +0.5 / −0.1 / −4.5 / +4.6 / +3.9 / −2.9 ms，即普通抖动 |

所以分组调用按 `-r = 声明值 + 1` 请求，只把**第一个**形状的首样本丢掉，其余样本
一个不少；被丢的值记在 `measured.json` 的 `discarded_warmup_ns`，`reported_avg_ns`
保留 llama-bench 自己的均值，`avg_ns` 由留下来的样本重算（两者不得对不上）。

逐形状进程保持历史口径：`-r` 就是报告的样本数，不丢任何样本。已发布的每一轮都是
这么测的，改它等于悄悄改掉所有存档数字的含义。

**测量必须在插电状态下进行**（2026-11-05 记）。这台是笔记本，电池供电时墙钟是另一个
量：当天的 OLMoE 试点整轮跑在电池上，同一条命令读 62.65 ms，插电的历史运行读 ~49 ms，
而且那一行**整行**都慢，看起来和"进程状态"一模一样。工具不查电源，靠人在开始前确认。

**「哪个是好行」不止一种读法时，斜率不算测出来。** 三个深度里若中间那个是坏行，
去掉它正好穿过另外两点，拟合残差为零——残差小并不说明它就是坏行。所以
`python -m composing decompose`（`composing/decompose.py`）把**所有**落在状态带内的
读法连同各自的斜率一起报出来，
并给出它们的斜率跨度；跨度不为零就不许把其中一个斜率当结论。

**不读历史的 stage 不许带深度噪声**（2026-11-05 追加，属 R4 的执行口径）。
decode 的 `projection` 与 `dense_ffn` / `moe_ffn` 只读当前 token，`visible_history`
改成 128、512、1024 计算量一个字节都不变。所以同一 kind 在这几个深度上的价格是
**同一个 op 的三次重复测量**，不是三个任务：

| 模型 | 表侧总斜率 | 其中 attention | 不读历史的 stage 贡献 |
|---|---|---|---|
| qwen3-0.6b | 16.098 | 15.928 | +0.170 |
| qwen3-1.7b | 14.275 | 13.703 | +0.572 |
| qwen3-4b | 30.383 | 41.991 | **−11.608** |
| granite-3.0-3b-a800m | 16.918 | 19.134 | −2.216 |
| qwen1.5-moe-a2.7b | 15.773 | 14.625 | +1.148 |
| olmoe-1b-7b | 10.096 | 7.547 | **+2.548** |

（µs/KV token，按 h128→h1024 弦长算，六个模型的已发布表。）这些差值会被模型乘上
128/512/1024 个 token 的历史，于是纯粹的表侧误差变成了"深度效应"。

规矩：**同一 op 的这几个条目必须报同一个价格**，由 `--history-invariant-price
median_of_history_replicates`（导出时）或 `reprice_history_invariant.py`（已导出的表）
给出，取数个深度的中位数，并在条目的 `physical_signature` 里写
`history_invariant_price_policy`。**这是一个估计口径，不是测量协议**：条目仍按原键
存放，被替换的每个读数留在 `export_report.json` 的 `history_replicates` 里，
重放价格表的 `source` 带上 `-replicated-median-` 前缀。默认（`own_shape`）逐位不变，
所有旧表不受影响。

三个拒绝条件：条目之间除深度外还有任何不同（kind/device/形状/workspace/协议字段/
签名的其余部分）就不是重复测量；少于两个深度没有可合并的东西；相对离散超过 50%
说明这不是抖动，先查。**合并后的表与旧墙钟不可比**（R11）：新表的预注册对照必须是
新测的墙钟。

比较斜率时用**同口径**：只有 attention 随历史变，所以 `composing/decompose.py` 的
主比值报 `slope_ratio_attention_only`，总斜率与 attention-only 的差单独列出。

## 3. 预注册的预期（测之前写，测完对照）

这三条是可被证伪的，不是结论：

- **P1** 三个 dense 模型的误差不会随参数量单调上升。理由：抽象以"逐形状实测
  成本"为单位，模型规模只改变形状，不改变合同。**若出现单调趋势，说明缺少某个
  规模相关的项（例如内存带宽层次），要当成缺陷报，不要解释成"大模型更难"**。
- **P2** MoE 的误差大于 dense。理由：路由是数据相关的，测量块把专家选择藏进了
  一个不透明的宏任务。
- **P3** 同一模型换设备后，绝对价格变、**策略序**大致不变，但决策裕度会变。
  这与 `decision_margin` 的边界一致（裕度属于机器）。若出现跨设备的序翻转，
  那是比误差更有价值的发现，要单独写。

## 4. 不许写的

- 不许把三个 dense 模型说成"验证了模型族"——它们是同一族、同一分词器、同一
  量化档，只差规模。
- 不许把 MoE 子图误差说成整层或整模型误差。
- 不许用 hybrid 模型的代表层误差推断整模型。
- 不许在新的设备上复用笔记本的价格后声称"预测了那台机器"。
- 不许把 `--allow-unstable` 产出的条目混进平均值。
